Dancing Figures Decision Guide

New scene · proposal

Dancing figures with swappable skins

Three decisions shape the scene; everything else follows from them. Each section lays out the options, what they cost, and how they land in the existing scene infrastructure. Pair this with the Dancer Lab page to see the options move.

The shape of the scene

A rig in TypeScript, a skin in GLSL

The "skeleton you can re-skin" idea maps onto a clean split. The rig is a joint hierarchy plus a choreography that turns the music clocks into joint positions — pure TypeScript, unit-testable like the geometry builders in meshGrid.ts. The skin is a GLSL function that draws a bone given its two endpoints. Skeleton, stick figure, neon, blob are all skins over the same rig; neither side knows about the other beyond the joint list.

TypeScript, per frameGLSL, per pixel

Music clocks

anim: AnimFrame

beatPhase, barPhase, tempoLock, lowPulse, sectionIntensity, dropPulse, profile — all already computed by animClock.ts.

Choreography

scenes/dancers/moves.ts

Picks and blends moves; each move is (clocks) → Pose (joint angles). Per-dancer phase offsets for a crowd.

Rig solve

scenes/dancers/rig.ts

Forward kinematics: Pose → joint positions, packed into one Float32Array for all dancers.

Upload

extraUniforms

The array goes up as uniform vec2 uJoints[N] via the extraUniforms hook — the same path caustics.ts uses for its ripple pool.

Skin

fragment shader

Per pixel: distance to each bone capsule, then skin(bone, d) colours it. uSkin selects the skin function.

Nothing in this chain needs a new GL path, instancing, textures, or asset loading — none of which exist in the codebase today. It reuses createFullscreenScene end to end.

Decision 1

Look — how the dancers occupy the screen

Flat 2D cutouts recommended start

Screen-space capsule bones, no lighting. Reads as a cartoon / paper-cutout skeleton.

  • Stylised look forgives procedural stiffness
  • Cheap enough for the gallery's always-on preview tiles at reduced detail
  • Runs on every quality preset — no minQuality
cost: one fullscreen pass, N×bones distance tests per pixel

2.5D stage rows cheap upgrade

Same 2D bones plus a per-dancer depth: scale, dimming, draw order, a perspective floor and a spotlight.

  • Turns a line of dancers into a stage — hero in front, crowd behind
  • Almost no extra cost over flat; can be a setting (stageDepth) rather than a fork
  • Depth cue makes the crowd read even when small
cost: flat + a few lines of shader

3D shaded figures later, if ever

Raymarched 3D capsules with lighting and self-occlusion, like ferrofluid.ts's sphere-trace loop.

  • Real turns, foreshortening, ground shadows
  • Per-pixel cost scales with dancers × bones × march steps — realistically one or two figures
  • Would need minQuality: "mid" and heavy gating on uMaxSteps
cost: ferrofluid-class raymarch per figure

Recommendation: ship flat 2D with the depth cues from 2.5D behind a setting. The rig is identical in all three, so a 3D skin path could be added later without touching the choreography — but it is a separate project.

Decision 2

Cast — one dancer or a floor full

Hero + backing crowd recommended

One large lead dancer doing the featured moves; a row of smaller dancers doing simpler moves, phase-offset so they don't march in step.

  • The hero carries the music-reaction; the crowd carries the energy
  • Crowd size follows ctx.quality.detail (the gridSizeForQuality pattern)
  • Natural home for a crowd setting with an auto weight on the density dial
cost: (1 + crowd) rigs, one shader pass

Single dancer

One centred figure; all detail budget goes to choreography and skin.

  • Simplest first milestone — the hero of the option above is this
  • Can feel sparse on a TV at low intensity
cost: one rig

Crowd only

Many equal dancers; variety from offsets and per-dancer move choice.

  • Great as a wall-of-motion at high intensity
  • No focal point for the beat — the eye doesn't know where to look
cost: N rigs

Recommendation: build single-dancer first as the milestone, then add the crowd. Hero + crowd is the shipped default; "crowd size 0" gives single, "hero off" gives crowd-only, so all three are one scene.

Decision 3

Choreography — where the dancing comes from

Both options are fully procedural. Baked animation clips (Mixamo-style) would need an asset pipeline that doesn't exist and sit badly with the "write it as independent work" rule, so they are off the table for now.

Move library + picker recommended

A handful of hand-authored moves, each a pure function of the bar/beat clocks. A picker escalates through them on sectionIntensity and crossfades; dropPulse overrides with a hands-in-the-air pose; tempoLock falling out returns to a free sway.

  • The dance changes over a track: build, drop, breakdown all look different
  • Moves are unit-testable (feet on the floor, no joint through the body)
  • Adding a move is adding a function — the natural growth path
effort: a few days of choreography tuning

Single layered oscillator

One pose built from stacked layers: bounce on beatPulse, sway on barPhase, arm height on intensity.

  • Ships in an afternoon; every layer is a slider
  • Every track produces the same dance at a different amplitude — wears thin fast
  • Useful as the crowd's move set even under the library option
effort: hours

Recommendation: library for the hero, oscillator-style simple moves for the crowd. The library's lowest rung is the oscillator, so this isn't really either/or.

Skins

What "skin" means, and the one UI gap

A skin is a GLSL function over the rig. The first set is procedural and needs no assets: skeleton (ivory capsules, skull, ribs, pelvis), stick figure (the reference skin — if a move looks wrong here, blame the rig), neon tube (glow falloff in the palette's accent, the most at home next to the existing scenes), and blob buddy (fat capsules with smooth-min joints, eyes). "Other characters" later means either richer procedural skins or, if they need artwork, a texture-loading path — new infrastructure, kept as its own step.

The one thing the settings system can't express today is a picker: SceneSetting.type only knows "boolean". Skin selection needs a small type: "enum" with an options list, touching sceneSettings.ts, deviceMenu.ts's setting row, and the protocol's value clamp. It stays a float uniform underneath (uSkin), so nothing else changes. The interim is an integer slider, which works but reads as "Skin: 2".

Risks

What could make it look bad

Stiffness
Procedural dance reads as robotic if poses are pure sines. Mitigations: ease curves per joint, a small per-dancer noise layer on top of the move, and the skeleton skin as the launch skin — jerky is on-brand there.
Beat loss
When tempoLock drops, a dancer stepping to a stale beat looks broken in a way a shader ripple doesn't. The picker must fade to a free sway driven by flowPhase, not freeze or keep stepping.
Preview tiles
The gallery renders every scene continuously at reduced detail. A crowd of 8 with 12 bones each is ~100 distance tests per pixel — fine on flat 2D, not on raymarched 3D. Crowd size must respond to detail.
Panorama
Multi-device Panorama slices the room; a dancer straddling a slice boundary must be positioned in room space via roomUv(), not per-device screen space, or the two halves won't line up.

Suggested path

Milestones

  1. Rig + stick skin, one dancer, oscillator move. Proves the upload path and the FK. Registered as a draft scene.
  2. Move library and picker. Sway, step, bounce, hands-up, drop; tuned with ?audio=synthetic&bpm= at slow, house and fast tempos.
  3. Skeleton skin + enum setting. The skeleton is the launch look; the enum setting lands alongside it.
  4. Crowd + stage depth. Quality-scaled crowd, 2.5D cues, auto weights for the settings above.
  5. More skins. Neon, blob; then decide whether character artwork justifies an asset pipeline.

Nothing has been built yet — this is the plan behind the Dancer Lab sketch. The lab's rig, move list and skins are the same ones proposed here, so what you see there is a faithful preview of what milestones 1–3 would produce.
